# P1-B 下一步路线：现在可以开始“真实研究”，但要走沙盒路线

## 结论

**可以开始做真实的东西了。**

但我建议你现在批准的，不是：

> “正式真实数据准入完成 → 开历史回测 → 开 AI 选股 → 准备实盘”

而是：

> **“P1-B Wave C：LOCAL CURRENT-OBSERVED REAL RESEARCH SANDBOX”**

也就是：

**真的股票 + 真的行情/财务数据 + 真的研究计算 + 真的三只股票研究报告**，但仍然：

`NON_TRADEABLE`  
`LOCAL_ONLY`  
`NO_ORDER`  
`NO_BROKER`  
`NO_PRODUCTION`  
`NO_HISTORICAL_PIT_CLAIM`

## 一个非常关键的判断：Historical PIT 不应该挡住“今天的真实研究”

这里要把两个概念彻底分开。

假设今天是 2026-10-06。

你今天从数据源拿到了：

- 过去 327 个交易日行情；
- 最近若干财报；
- 当前行业分类；
- 当前复权因子；
- 当前可见的公司行动数据。

我们**不能**因此声称：

> “我知道 2025-06-01 当天，当时的人一定能看到今天返回的同一个财务版本。”

这就是你的 Gate 一直坚持的：

`historical_visibility_proven=false`

这个坚持是正确的。此前报告也明确区分了“今天抓到的历史值”和“当时历史 cutoff 已可见的值”。fileciteturn0file2

但这并不妨碍另外一件事：

> **在 2026-10-06 今天，我可以用今天已经看得到的历史行情和财务信息，研究“我今天怎么看这家公司”。**

这是两种完全不同的研究：

**Current-observed research：**

> “站在今天，我怎么看 603993？”

可以做。

**Historical as-of backtest：**

> “假装回到 2025-06-01，当时我的系统会不会选中 603993？”

暂时不能做。

所以我不建议再让整个 P1-B 被：

`historical PIT 尚未完成`

卡住。

应该改成：

> **Current Real Research = 可以继续推进**
>
> **Historical Backtest = 继续 BLOCKED**

这是当前最重要的路线调整。

### 建立独立的 Real Research Sandbox

这里我不建议为了赶进度，把现在 `QUARANTINED/BLOCKED` 的 gateway 数据直接偷偷塞进正式 `ResearchCard`。

那样会破坏你前面花这么大力气建立的信任边界。

正确方法是新增一个明确的沙盒层，例如：

```text
LOCAL_EXPERIMENTAL_REAL_RESEARCH
```

它可以读取当前网关已经捕获并通过工程 DQ 的真实数据，但必须保持：

```text
source_admission = UNVERIFIED_GATEWAY
purpose = LOCAL_EXPERIMENTAL_RESEARCH
historical_visibility_proven = false
cloud_transfer = false
tradeable = false
can_produce_order = false
production_eligible = false
```

它的输出不要叫正式 `ResearchCard`。

可以叫：

```text
RealResearchSandboxReport 1.0
```

或者：

```text
ExperimentalResearchAssessment 1.0
```

这样系统第一次真的研究股票，同时又没有撒谎说：

> “这是一份经过正式数据许可/PIT认证的 Production ResearchCard。”

## 现在真正需要保留的一道 Gate：这个月卡网关不能冒充“Tushare 官方直连”

这里经过这次 deep research，我认为必须给你一个比较重要的新结论。

Tushare 当前官方数据服务协议写得比之前我们看到的宣传页面严格得多。

官方协议明确写明：付费权限应通过 Tushare 账户获得；禁止通过非 Tushare 指定方式开通服务；并称其没有授权第三方销售/转让服务资格；许可被描述为个人、不可转让、非商业、有期限的使用。citeturn3view0

而你拿到的是：

> 自定义 IP gateway + 自定义 token + 改写 SDK `_DataApi__http_url`

与此同时，Tushare 当前公开 MCP 文档给出的官方 MCP 示例地址是在 `api.tushare.pro` 的 HTTPS endpoint，而不是你现在那个自定义 IP 网关。citeturn4view0

这**不能证明你的月卡有问题**——销售方可能有某种我们尚未看到的授权安排。

但也绝对不能由此证明：

> `118...:8030 = 官方 Tushare`

所以 Codex 现在把它叫：

```text
TUSHARE_MONTHLY_GATEWAY
OWNER_PROVIDED_MONTHLY_GATEWAY
```

而不是：

```text
OFFICIAL_TUSHARE_DIRECT
```

是正确的。

另外，Tushare 自己的 AI 指南又明确宣传了本地落库、策略回测、AI 投研工作流，而且建议关键投资数据与第二来源交叉验证。citeturn3view1 这与服务协议中更狭窄的“个人查看”措辞存在需要进一步澄清的地方；因此，在你的具体月卡渠道和 gateway 身份没有澄清之前，我不会建议工程里写：

```text
license_verified=true
```

这是谨慎的合同解释，不是说“不能继续研究”。

**正确处理方法就是：**

正式 `ADMITTED` 继续严格。

同时开一个：

**LOCAL EXPERIMENTAL REAL RESEARCH SANDBOX**

这样 provider 问题就不再卡死整个项目。
